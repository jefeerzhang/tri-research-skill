# 客户端装配与结果截断上限各收进单一出处

「清 proxy → 查 SDK → 解 key → 建 client」这四步此前抄了 **8 份**：`_search_cli`
的 `Backend.client()` / `check` / `run_managed_command`，`_search_registry` 的
`_resolve_backend` / `search` / `check`，`required_backends._serpapi_gap`，
以及 serpapi skill 的 `load_key`。每份都在自己决定「第一次请求之前什么算不可用」，
于是同一件事长出不同说法：managed 命令先报缺 key、`client()` 先报缺 SDK，
Registry 的 `check` 与 CLI 的 `check` 对 `--no-proxy` 一个清一个不清。
截断上限同理抄了 **2 份**——`_search_registry` 自带 `_SNIPPET_LIMIT` /
`_CONTENT_LIMIT`，`search_backends` 直接写 `[:500]` / `[:5000]`：同一条结果
从哪条泳道取回来，就被截成不同长度。

决定：条件的**判定**住进 `Backend.client()`（SDK 在场 → key 可解析 → 构建），
失败以 `ClientSetupError`（`SdkMissing` / `KeyMissing`）**抛出**；条件的**呈现**
仍归各条泳道——`search` 印 `{"error": …}` + exit 1，`check` 印
`{"available": false, …}`，SerpApi 写 stderr + 退出码，Required 门禁把失败
收集成一条 gap 文本。上限与 `truncate()` 住进 `_search_cli`，两条泳道共读。
顺带清掉两处 ADR-0004 之后的残留：`BackendSpec.env_key`（与
`Backend.env_key` 重复申报，Registry 读的是自己那份）、serpapi `load_key` 里
自己拼的 `.env` 路径。`_run_with_timeout` 改公开名 `run_with_timeout`——
门禁与 Registry 都要用它，超时语义也必须一致。

## Considered Options

- **把 CLI 全量收编到 Registry（一条搜索路径）**：ADR-0003 已定界——`_search_cli`
  是 Agent 的命令行表面，Registry 是程序化 seam，两条路的错误契约故意不同。
  收编要动所有子代理消费的输出形状，重开条件（出现第二个程序化消费方）尚未满足。
- **让 `Backend.client()` 自己印 JSON 并退出**：省掉 8 处 try/except，但把三种
  方言焊成一种，SerpApi 的「stderr + exit 1/2/3」契约和 Required 门禁的
  「收集全部缺口」语义都会丢。抛异常才留得住各自的表情。
- **（采用）条件一处判定、方言各自渲染**：`api_key()` 作为可单独使用的半边——
  SerpApi 的 client 只是钥匙持有者，真正的 `requests` 在取数时才碰，硬并
  `client()` 是给不存在的步骤造抽象。
- **`required_backends` 保留自己的 key/SDK 判断**：它确实不建 Exa/SciVerse 的
  client（只用 `find_spec` 探 SDK），但那两处「不建」与这里的「建」迟早会对
  「什么算就绪」给出不同答案。现让 SerpApi 半边改走 `client()`，Exa / SciVerse
  的 key + `find_spec` 组合保持原样（它们没有客户端可装配）。
  **部分被 ADR-0011 演进**：Exa 门禁改为转接 `Backend.client()`；SciVerse 仍用
  KeyProvider + `find_spec`（不是 Web Backend，没有 `client()` 可转）。

## Consequences

- **行为变化（三处，均为收窄）**：
  1. SerpApi `batch_search` 缺 key 时 fail-fast——原来每条 query 各产一份
     `{"error": …}` 且**仍以 0 退出**，现在第一条请求发出前就 exit 1。
  2. `Registry.batch_search` 遇装配失败直接抛（`ClientSetupError` 是
     `RuntimeError` 子类，程序化调用方仍只捕一个异常族），不再摊成 N 份错误 dict。
  3. Required 门禁在「SDK 与 key 同时缺」时先报 SDK 缺失（与其余泳道同一顺序，
     ADR-0002）；只缺 key 时文案逐字不变。
- `search_backends.strip_ref_meta` 仍自带「层级 / 来源」的剥离正则：那是 LaTeX
  排版的取字，不是契约判定（字段读取走 `_report_parse.Reference`），属有意保留。
- `sys.path` 样板（同 skill 内直接脚本调用）继续不合并。跨 skill 的 serpapi → `_search_cli` 已收进 `tri_research_runtime`（ADR-0015）；Evidence Ledger / Registry 仍走兄弟 `scripts/`。
- Managed extras 的 `[:1000]` / `[:20000]` 收成 `CITATION_TEXT_LIMIT` / `EXTRACT_CONTENT_LIMIT`，与 `SNIPPET_LIMIT` / `CONTENT_LIMIT` 同住 `search_cli`。
- `_run_with_timeout` → `run_with_timeout` 是公开改名，`required_backends` 与
  Registry 同步换名；无兼容别名（仓内调用点全在同一轮里改完）。
- 同一条规则在报告侧的落点见 CHANGELOG 的 `_report_parse` 与
  `EvidenceAuditFailed` 两条：一次判定，多方读取。
- 测试：`tests/test_backend_key_resolution.py`（抛类型、search 方言、SDK 先于
  key、factory 抛异常时 check 不 traceback）、`tests/test_search_registry.py`
  `RegistryBootstrapTests`（batch 一次都不发 query、check 报 available:false）、
  `tests/test_host_helpers.py` `ClientBootstrapConsolidationTests` /
  `ResultTruncationConsolidationTests`（源码闸门：装配标记与上限声明全仓只出现
  一次，任何泳道都不得再手抄）、`skills/serpapi/tests/test_serpapi_cli.py`
  `test_batch_search_fails_fast_before_any_fetch`。
